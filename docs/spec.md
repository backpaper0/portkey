# portkey 仕様書 (v1)

本ドキュメントは、[マップ「portkey: 実装可能な仕様書とアーキテクチャ決定をロックする」](https://github.com/backpaper0/portkey/issues/1)で行われたすべての決定を、実装に着手できる粒度でまとめたものである。

用語は [CONTEXT.md](../CONTEXT.md) の定義に従う。本書はその用語を前提として仕様の詳細を記述する。

## 1. スコープ

- portkey本体(プロキシソフトウェア)の設計・実装のみを対象とする。
- portkeyを使う側の運用(Dockerコンテナの起動方法、コーディングエージェントのサンドボックス化手順など)はスコープ外(別エフォート)。
- v1はサンドボックスコンテナ**内部**で動作し、**同一コンテナ内**のプロセスへのみプロキシする単一コンテナ構成のみをコアスコープとする。複数のサンドボックスコンテナを1つのportkeyがまとめて相手にする発展的な使い方はv1のスコープ外(将来必要になれば別エフォート)。
- v1はbackpaper0さん個人のDocker運用での利用を最優先し、将来のOSS公開は意識しつつ汎用化は最小限に留める。

## 2. アドレッシング方式

サブドメインルーティングのみを採用する(パスルーティングは不採用)。

```
http://<アップストリーム識別子>.localhost:<ゲートウェイポート>/...
```

- パスルーティングを採用しない理由: アップストリーム側アプリが絶対パスで静的アセットを参照している場合、パスプレフィックスの剥離だけでは壊れる。サブドメインルーティングならパスをそのまま透過できる。
- TLDには `.local` ではなく `.localhost` を採用する。RFC 6761によりどんなサブドメインでも常に `127.0.0.1` へ解決される規定があり、mDNSレスポンダーの自作など追加の名前解決の仕組みが不要になる。

### 対応ブラウザ/OSバージョン

RFC 6761の`*.localhost`ループバック解決規定は、Name Resolution APIs/Librariesへの`SHOULD`止まり(Application Softwareへは`MAY`)であり、`MUST`の保証ではない([調査結果](https://github.com/backpaper0/portkey/blob/research/localhost-wildcard-resolution/docs/research/localhost-wildcard-resolution.md)、issue #10)。

- Chrome/Firefox(現行版): ブラウザ自身が`*.localhost`をハードコードしてループバック解決するため、あてにできる。
- Safari/WebKit: 2016年から続く「ワイルドカードサブドメインを解決できない」バグがあり、OS側の修正は**macOS 26 "Tahoe"(2025年秋)以降**。それより前のmacOS上のSafariは非対応。

→ 仕様書上のサポート対象は「Chrome/Firefox 現行版、macOS 26以降のSafari」とし、それ以前のSafariはサポート対象外と明記する。

### DNS解決に関する制約(ADR-0001)

[ADR-0001](../docs/adr/0001-never-resolve-localhost-suffix-via-dns.md)により、portkeyはアップストリームへ実際に接続する際、`Host`ヘッダーに含まれる`.localhost`サフィックス付き文字列をそのままDNS解決(`dns.lookup`/`net.connect`等)に渡してはならない。接続先は識別子から抽出した生のホスト名(v1では常に`localhost`)を直接使う。

理由: Node.jsの`dns.lookup`はOSの`getaddrinfo`に完全委譲するため、Alpine(musl libc)やWindows環境では実際に外部DNSへの問い合わせが発生し得り、`.localhost`という文字列自体の解決に依存する実装は環境によって壊れる。

## 3. アップストリーム識別子のパース仕様

`<ホスト名>_<ポート>` 形式。

### 文字種・書式

- ホスト名部分: DNSホスト名相当(RFC 952/1123準拠)。英数字・ハイフン・ドット区切りラベルのみ許可し、各ラベルの先頭/末尾にハイフンは不可。
- ポート部分: `1`〜`65535`の範囲の10進数のみ。先頭ゼロ(例: `03000`)は不正。
- セパレータ`_`はちょうど1回のみ出現を許可する。0回または2回以上は不正な識別子として扱う。セパレータに`_`を採用する理由([ADR-0002](../docs/adr/0002-underscore-as-upstream-identifier-separator.md))は、ホスト名部分の許容文字集合に`_`が含まれず、`~`(Chromeの`*.localhost`ワイルドカード名前解決を壊す)・`-`(ホスト名自体がハイフンを含みうるためパースが曖昧になる)のいずれの問題も回避できるため。

### 大文字・小文字

ホスト名部分は大文字小文字を区別しない。portkeyは内部処理の前に小文字へ正規化してから比較・接続に用いる。

### `Host`ヘッダーからの抽出ルール

1. 末尾の`:<ゲートウェイポート>`は単に剥がして無視する。実際の待受ポートとの一致検証は行わない(ゲートウェイポートは常に1つしかなく検証に実用上の意味がないため)。
2. ポートを除いたホスト部分が厳密に`localhost`と一致する場合 → **コンソール**へのアクセスとして扱う。
3. `.localhost`で終わり、かつ直前の部分が上記の文字種・書式ルールを満たす有効な`<ホスト名>~<ポート>`識別子である場合 → **アップストリームルーティング**として扱う。
4. それ以外(パターンに一致しない、`.localhost`で終わらない等) → **不正なリクエスト**として`400 Bad Request`を返す(§4参照)。

## 4. エラーレスポンス仕様

### 400 Bad Request(不正なアップストリーム識別子)

- §3の抽出ルールに一致しないリクエストに対して返す。
- ボディはプレーンテキスト(または簡素なHTML)で「不正なアップストリーム識別子です」という趣旨のメッセージのみを返す。内部情報は含めない。
- アップストリームに接続できない場合の`502 Bad Gateway`とは明確に区別する。

### 502 Bad Gateway(アップストリームに到達不能)

- アップストリームへの接続が失敗した場合(未起動・タイムアウト等、理由を問わず一律)に返す。
- ボディはプレーンテキスト。内容はリクエストされたアップストリーム識別子をエコーバックする一律メッセージとする(例: `Bad Gateway: <アップストリーム識別子> is not reachable`)。
- 接続拒否/タイムアウトの理由区別は行わない(詳細はアクセスログ側に委ねる)。トラブルシューティングのヒント文言は入れない。

### タイムアウト

- 接続タイムアウト(TCP接続確立まで)のみを設ける。読み取り/アイドルタイムアウトは設けない(WebSocket/SSEのストリーミング・ロングポーリングを誤って切断しないため)。
- 既定値: 5秒。
- 環境変数・CLIフラグで上書き可能(§6の設定方針を参照)。

## 5. 対応プロトコル・セキュリティスコープ

- HTTP(GET/POST等の一般的なメソッド)を透過的にプロキシする。
- WebSocket/SSE(Upgradeリクエストの透過)はv1スコープに含める。
- HTTPS対応はv1スコープ外。
- 認証機構は持たない。
- portkeyプロセス自体は`0.0.0.0`でリッスンする(Dockerのポートフォワーディングを受け取るため、`127.0.0.1`限定にはできない)。
- 「外部ネットワークに公開しない」という安全上の制約は、portkey自身のバインドアドレスではなく、Dockerの`-p`でホスト側のみにマッピングする**運用者側の責任**とする(portkey自体はこれを強制しない)。

## 6. デプロイ配置

- portkeyはサンドボックスコンテナの**内部**で動作し、同じコンテナ内の他プロセス(常に`localhost`)へプロキシする。
- v1コアスコープは単一コンテナ構成のみ。
- アップストリームのホスト名は実質的に常に`localhost`だが、識別子のフォーマット自体(§3)は汎用文字列として定義し、将来の拡張(複数サンドボックスコンテナ対応、別エフォート)を妨げない。

## 7. 実行環境・配布形態

- 実行環境: Node.js + TypeScript。
- 配布形態: npm registryへの公開は見送り、GitHubから直接インストールする形態のみ(例: `npx github:backpaper0/portkey`)。
  - 理由: npmの`portkey`という名前は既に無関係な別製品(Portkey AI社のゲートウェイ/エージェント向けCLI)に使われており、名前衝突による誤認リスクがある。また今回は基本的に個人用ツールであり、npm公開の必要性自体が薄い。

## 8. 設定方法

環境変数 + CLIフラグで設定する。設定ファイルはv1スコープ外。

| 設定項目 | CLIフラグ | 環境変数 | 既定値 |
|---|---|---|---|
| ゲートウェイポート | `--port` | `PORTKEY_PORT` | `1541` |
| 接続タイムアウト(秒) | `--connect-timeout` | `PORTKEY_CONNECT_TIMEOUT` | `5` |

(接続タイムアウトの具体的なフラグ・環境変数名は、issue #9で示された「`--port`/`PORTKEY_PORT`と同様の命名パターンを踏襲する」方針に基づき本書で確定した。)

## 9. ログ

標準出力への最小限のアクセスログのみを出力する。構造化ログや外部送信は将来検討(v1スコープ外)。

## 10. コンソール画面(`/`)

### 実装方針

- ビルドステップなしの素のHTML(サーバーサイドで生成する単一ページ)+ 最小限のvanilla JSで実装する。フロントエンドフレームワーク/バンドラーは導入しない。

### UX

採用案(A案: 単一カラム・最小フォーム。プロトタイプは`prototype/console-ux`ブランチの`docs/prototypes/console-ux-prototype.html`の`?variant=A`を参照):

- ホスト名とポートを1つのコンボ入力(`<ホスト名>` `_` `<ポート>`)で受け取る。
- 入力に応じて生成されたURLをフォーム直下に即座に表示する(サーバーサイド生成ページ上でJSにより動的に組み立て)。
- 生成されたURLはクリックでクリップボードにコピーでき、コピー後は短時間フィードバック表示(ボタンラベルの変化)を行う。
- 用語説明・使い方は`<details>`による折りたたみに格納し、初見時の画面情報量を最小限にする。
- ホスト名・ポートのバリデーション(§3のパース仕様準拠)エラーはコンボ入力の直下にヒントとして表示する。

## 11. テスト戦略

仕様書には「何を仕様として保証すべきか」(=本書の§2〜§6)のみを記載する。具体的なテスト技法(単体/統合、モック有無、フレームワーク選定等)の選定は実装フェーズに委ねる。

## 12. スコープ外(Out of scope)

- パスルーティング方式(§2で不採用と判断)。
- 複数のサンドボックスコンテナを1つのプロキシがまとめて相手にする発展的な使い方(§1、§6)。将来必要になれば別エフォートとして扱う。
- HTTPS対応。
- 認証・アクセス制御機構。
- 設定ファイルによる設定。
- 構造化ログ・ログの外部送信。
